# React catalog and player

Open `http://localhost:8000/react` or `/react/` after `npm run dev`. React uses the shared catalog/IndexedDB service and owns its YouTube players. The legacy player remains available directly at `/`; React is the parallel preview route.

## Routes and data

The mounted client HTML and `/react/assets` boundary are unchanged: HTML is `no-store`, assets revalidate, and unknown/private paths are plain 404s. Root `/listCount`, `/cacheState`, and `/refreshPlaylists` remain the shared server API; development uses the same origin and needs no proxy. `channelId` scopes requests and IndexedDB records. API credentials remain server-only.

`client/src/hooks/useCatalog.ts` owns a `CatalogSync` and `IndexedCatalogStorage` instance per mounted channel. Saved data renders without waiting for server checks, with loading/checking/refreshing/offline/error messages, Retry, empty/no-match states and freshness text. Status and Retry appear below the list, so background checks and selections cannot move its rows. The routine ready message is hidden. Per-playlist video counts remain internal for playback selection. BroadcastChannel and focus/online/visibility/pageshow events revalidate the catalog. Effect cleanup closes storage/notifications, removes listeners and aborts requests; StrictMode remounts cannot adopt old results or duplicate an import. The existing 12-hour policy, bounded refresh polling and failure cooldown remain unchanged.

Local reads and metadata checks start concurrently. Healthy saved data renders without awaiting the network; a 100 ms grace period lets that read avoid downloading an unchanged full catalog. Slow local storage cannot block a server response, and transient open failures can recover to persist the downloaded snapshot. Late reads are fenced by channel/version and can restore offline browsing after a failed check. The footer does not claim no saved data exists while startup is pending.

The prototype DataFetcher and `window.listData` dependency were removed from React. The legacy page and its entry remain independent.

## Player ownership and selections

`YouTubePlayer` owns a private `PlaylistPlayer` controller and a stable host. It does not publish `window.player` or import the legacy DOM-mutating entry. The shared SDK script promise loads on the first explicit selection, with retry after a failure and a 15-second deadline. Each controller has a separate readiness deadline and generation checks for old callbacks.

Explicit selection resolves an ID through the latest catalog before queueing it. The newest queued choice wins; initial player readiness revalidates that choice again. Removed choices leave existing playback alone. Normal playlists start at a random valid index and enable shuffle/loop. Boss playlists start at zero and explicitly disable shuffle, including after a normal playlist. Playing/paused/buffering states update the heading, unavailable-video events skip forward, and autoplay blocking displays a request to press Play in the embedded player.

Player interactions request catalog metadata checks. Background catalog changes never recreate, stop, reload, or seek the player and do not rename the currently playing selection. Only a new explicit selection can load a playlist. Disposal destroys the player, clears its timer/host and invalidates pending API/selection callbacks. Back/forward-cache preservation uses pageshow revalidation rather than treating a cached page as a new mount.

With a single player or an independently Added secondary, clicking either loaded row pauses playing/buffering media or resumes paused/cued/ended media with `pauseVideo`/`playVideo`, without reloading the playlist or changing its position, random start or shuffle settings. The control runs in the click/keyboard gesture without waiting for the background metadata check. Pausing during buffering updates the UI immediately, ignoring late buffering events while the pause is awaiting acknowledgment. Late PLAYING events from a player still awaiting its pause acknowledgment cannot undo a Swap. Same-row clicks during initial loading toggle the queued playback intent; a parked player cues paused when ready. Different rows resolve fresh catalog data before loading, and errored playback can be retried by selecting it again. A newer active-row click cancels any pending selection of another playlist. Heading/state icons continue to follow player events, including autoplay-blocked feedback.

Each row has separate Add, Swap and Favorite icon buttons with accessible names and hover tooltips. Add starts the chosen playlist in the secondary player while leaving the main stream running. Swap pauses the main player and resumes the selected playlist on top, parking the old main underneath. If that playlist is already loaded, neither iframe is moved, recreated, reloaded or sought: stable physical slots use CSS order to change their visual positions. Switching back preserves both streams' current videos, pause points and shuffle state. A new third playlist replaces the secondary slot; this is a two-player deck, not an unlimited playback history.

Add establishes independent playback mode. If a secondary is already occupied, unloaded rows show the plus icon with a small swap indicator and a replacement tooltip: Add replaces that secondary, preserving the main. Swap establishes exclusive playback mode. In that mode, either loaded row reverses the pair, pausing the current main and resuming the parked stream. Each header keeps a separate play/pause button and Swap button. Header pause stops only that player; header resume starts that player and, in exclusive Swap mode, pauses the other before resuming. Native iframe resume also pauses the other stream; native pause still allows the listener to stop playback. A later Add replaces the secondary and returns to independent controls. Removing either player clears the pair's mode.

When adding or replacing a secondary, the main's current volume and mute state are captured and applied before the secondary loads its playlist, including a zero volume. The readiness revalidation keeps that audio snapshot. Later volume changes remain independent, and ordinary swaps preserve each player's existing volume. Failed/unavailable audio controls do not block playback. The official [volume API](https://developers.google.com/youtube/iframe_api_reference#ChangingThePlayerVolume) reads and sets 0–100 volume separately from mute; a future half-volume option can use the same API. No volume slider, continuous volume linking or automatic half-volume is added here.

For a loaded playlist, Add becomes a minus/Remove button, with matching accessible name and tooltip. Removing it destroys that player's embed and clears its queued work, so late readiness callbacks cannot start removed media. Removing the secondary leaves the main untouched; removing the main promotes the remaining player without changing its playback state. Removing both restores the empty main placeholder. Adding another playlist replaces the current secondary even after swapping the physical player slots, and the replaced row becomes Add again. Remove also cancels an in-flight replacement request.

The secondary player is absent until needed. Both loaded players have independent pause/resume controls, and the header also offers Swap players. If only the secondary remains playing, it becomes the main; two simultaneously playing streams retain their current order. Both embeds stay visible, including while paused, and each has its own autoplay-blocked feedback. The API is configured with `autoplay: 0`; starting either stream requires an explicit selection/action. Browser autoplay restrictions may still require pressing Play in that embed. Playback positions are retained for the current page session, not saved across reloads.

Favorites use stable playlist IDs and channel scope in the separate `playlist-organizer-favorites` IndexedDB database. They sort alphabetically above the other alphabetized rows and survive upstream renames and browser reloads. Search and pagination include both groups. Alphabet jumps prefer the normal alphabetical group, falling back to favorites if no other row has that initial. Favoriting never starts playback and restores keyboard focus after reordering. Delayed storage reads cannot overwrite newer clicks; writes are serialized, and unavailable storage leaves favorites usable in memory. Favorites are local browser preferences, not shared account/session state.

Selection events call an existing `window.gtag` safely using friendly playlist labels. React does not load another Analytics tracker; the legacy tracker is unchanged. A blocked tracker or optional player setting cannot throw through the selection flow.

The scoped stylesheet supports the desktop two-column and mobile single-column layouts. Native links support keyboard selection and visible focus. Search and 100-row pages bound rendered rows while preserving sorted labels. These controls do not download the catalog again or alter playback; server responses still contain complete catalogs, so bounded API queries remain future work.

The magnifying-glass button sits beside the player heading and floats at the viewport edge if that heading scrolls away. It toggles an inline search bar directly below the heading and has a filled active state while expanded. Filtering applies after 300 ms without edits (after composition ends for IME input), resetting pagination while preserving playback. Enter applies the current text; Escape or clicking the icon collapses the bar while retaining the filter. Clear removes the filter. The playlist list remains interactive while the bar is open.

Open/collapsed state and search text persist per default/explicit-channel scope in the separate `playlist-organizer-ui` IndexedDB database, in its `search` store. A late saved preference cannot overwrite a newer user interaction. Writes are serialized and drained on disposal; storage failure leaves the controls usable in memory. The catalog database/version and playback state are independent of these preferences. Pending debounce timers and visibility observers are cleaned up on unmount.

A fixed alphabet rail sits beside the right edge of the list, before the page scrollbar. Available letters jump to and focus their first matching playlist, selecting the correct 100-row page if necessary. Missing letters are disabled; `#` handles numeric/symbol initials such as Intro, and accented Latin initials map to their base letter. The rail follows the current search results and refreshes, without loading or changing playback or requesting another catalog. List padding reserves space on desktop/mobile, and the rail scrolls internally on short viewports so it stays clear of the floating search icon.

Loaded playlist links show worded state tags such as Playing, Paused and Buffering. Tags and the playback action button beside each player's heading share its state colors: green for the main playing, blue for the secondary playing, yellow for either paused, red for buffering/loading/error. The header button shows the action available (Play when paused, Pause when playing/buffering), while the tag describes current activity. This play/pause button is separate from the header's Swap button in both playback modes. Its icon and border match the heading, including in light/dark themes and after role swaps. The main row has `aria-current`; the secondary has a dashed border and an explicit Secondary tag/accessible description. Ordinary list actions, search and the alphabet rail retain their blue accent. Player-reported IDs preserve markers through renames/background refreshes, and search/paging can hide and restore loaded rows without touching playback.

App buttons have descriptive native hover tooltips; the clear control uses an icon with an explicit accessible name. Playlist links keep their names and use screen-reader-only descriptions for their state and play/pause/resume/retry action, without a `title` or visible hover tooltip.

Each catalog has one row per YouTube playlist ID. Old incremental caches can retain several labels for the same ID (such as City and City / Downtime); shared normalization consistently keeps the first alphabetic label with its own metadata, without altering freshness or combining counts. Processing deduplicates before counting, SQLite reads/writes normalize existing snapshots, and the browser parser also normalizes previously saved IndexedDB data. The list renderer independently enforces ID uniqueness before search and paging, including callers supplying raw unnormalized data. A later successful refresh replaces old names with current upstream names. Different IDs remain separate even if their labels look similar.

## Verification and limits

- **182 Jest tests** in thirteen suites, three existing legacy TODOs; strict source/test projects, lint and coverage gates pass. Deck tests cover role/mode changes, header transport versus row swaps, retained selections, audio snapshots, delayed lookups, request cancellation, removal and disposal. Jest percentages cover the selected server/shared/controller modules, not React's DOM execution.
- Chromium coverage uses API/player fixtures and actual IndexedDB. React cases include slow startup, offline/storage failure, retry, empty/text-safe catalogs, processing polls, channels, legacy/React cross-tab updates, queued/fresh/removed selections, shuffle/loop/error behavior, API/readiness failures, late callbacks, StrictMode cleanup/remounts, keyboard/mobile layout and 100K-row rendering/search. Player cases also verify light/dark active-row colors, accessible state badges, immediate mouse/keyboard toggles during slow metadata checks, control failures/retries, cancellation of pending choices and marker preservation through refreshes/filtering.
- A development-only browser fixture provides mount/unmount controls for lifecycle tests. Those controls are absent from the product bundle. The mobile screenshot is attached to the HTML test report.
- Dual-player cases verify simultaneous Add, both directions of Swap, unchanged iframe identities/positions/load calls, queued-paused readiness, replacement of a third playlist, independent controls/autoplay feedback, delayed pause events, and cleanup of both instances. Favorites cases use real IndexedDB for persistence, channel isolation, rename handling and delayed reads, plus memory-only fallback. Desktop/mobile screenshots verify green header/row styling, 44px icon controls and embeds staying within the player column. The opt-in 100K case additionally checks pinning and alphabet jumps; its [sample and limits](../benchmarks/README.md#react-catalog-rendering) are recorded separately.
- State-control cases exercise worded list tags and matching header action colors in light/dark themes, mouse/keyboard reversal of exclusive swaps, native resume exclusivity, returning from Swap to independent Add, replacement indicators, and delayed PLAYING events. Volume tests verify equal initial volume before load, copied mute/zero volume, replacement of a reused slot, independent later changes and audio-API failures.
- `npm run test:client` uses the actual built Express/client with fixture APIs and the shared fake IFrame API. It verifies routes, reloads, playback setup, catalog-only updates during playback, and navigation back to legacy, with no live YouTube quota. Startup/runtime and disposable build/watch/cache-isolation checks pass.

The [isolated desktop sample](../benchmarks/results/react-catalog-baseline.json), on Node 24.22.1 / Chromium 156 and the recorded i7-8700K, loaded 100K synthetic lists with 100 rendered rows in 907 ms, changed pages in 63 ms and searched in 70 ms. One catalog payload was fetched. This is one browser/automation observation using mocked API responses; it does not establish production HTTP throughput, network latency, or memory budgets.

Before group testing/cutover, manually check real YouTube audio, shuffle/loop, unavailable items, autoplay, phones and keyboard use, then validate remote CI and host routing. Real media delivery and worldwide playback conditions are not simulated by the fake player. Accounts/follow-DM sessions and durable account storage remain later work.
